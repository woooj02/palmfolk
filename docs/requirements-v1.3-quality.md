# Palmfolk: Requirements v1.3, part 2: accessibility, technical, polish

Part 1 (concept, valley, puzzles, return loop, eyes, Table mode): [`requirements-v1.3.md`](requirements-v1.3.md).
Rows marked **v1.3** are new or changed since v1.2. Numbers are starting values until the headset sets them.

## Accessibility (supports Experience Design and the Accessibility Forward award)

| ID | Requirement | Pass test |
|---|---|---|
| **A1 v1.3** | **A menu either hand can reach, or neither has to.** A small waystone post on the near edge of the valley, poked with any finger of either hand, or chosen by look and pinch with the hand at rest (GZ2). It covers pause, resume, restart, replant, mode, settings, x-ray, the visitor bell and quit. | A full session, including every menu action, can be done with only the left hand, and separately with only the right, by poke and by look and pinch. |
| **A2 v1.3** | **Everything works with one hand:** planting, all six puzzles and all five visitors. | One uncoached tester finishes Chapter 1 and one visitor with each hand alone. |
| **A3** | **Either hand, with no setting needed. Ownership is locked during an interaction.**<br>• **Choosing a hand:** while idle, the active hand is whichever engages first: it's nearer the active anchor or traveler and it connects (T2).<br>• **Keeping control:** that hand keeps control the whole time it supports a traveler or builds. The other hand approaching never takes over.<br>• **Releasing control:** after the build completes or is cancelled, the traveler is set down, or recovery ends (T5).<br>• **Who can re-align:** during T5 recovery, only the owning hand can re-align with the ghost hand. | Left-only, right-only and alternating runs all complete. Bringing the other hand close during a build or carry never interrupts it or transfers control. |
| **A4 v1.3** | **Build tolerance and fit.** Tremor-tolerant building (T3), adjustable stillness tolerance (3 steps), adjustable world scale. Height and reach are set by planting and changed by replanting, at any time, without losing progress. | A tester with mild tremor completes every build at default or adjusted settings. Replanting mid-puzzle keeps every bridge. |
| **A5** | **Reduced motion** turns off camera moves in the end sequence, the swaying of the world, and particle bursts. | With the option on, there's no camera motion that the player didn't cause. |
| **A6** | **Captions** for all meaningful sounds (build done, connection locked, refusal, chime, visitor arriving). | Every audio cue in P2 has a caption when captions are on. |
| **A7** | **Cues that don't rely on colour.** Refusal, connection, capacity and need signs (GZ1) are each shown by shape and motion as well as colour. | Every state can be told apart in a greyscale capture. |
| **A8** | **High-contrast mode** for routes, anchors, travelers and refusal cues. In Table mode it also adds a solid backdrop behind the valley. | Every state can be told apart with the option on, over a cluttered real table. |

## Technical Implementation (25%)

| ID | Requirement | Pass test |
|---|---|---|
| T1 | **Hand-route model.**<br>• Each finger is a polyline through its joints.<br>• The palm is a bounded polygon fitted to the wrist and metacarpals.<br>• The walkable side is the one facing up, measured against world gravity.<br>• Each traveler stores (surface, parameter) and is re-projected every frame, offset by the finger's radius. | No sliding, popping or sinking into the hand. |
| T2 | **Route graph with two thresholds:** connect below about 2 cm after holding 150 ms; break above about 4 cm. | No flickering connections. |
| T3 | **Bridge snapshot and build rules.**<br>• **Stillness:** filtered fingertip speed below 3 cm/s (One Euro filter), averaged over 0.5 s.<br>• **Commit as you build:** the bridge is built in sections from the anchor outward. Each section is frozen when progress passes it. Frozen sections never move again.<br>• **Uncommitted sections** follow the current filtered route.<br>• **Harmless tremor:** movement within the stillness threshold and 1.5 cm of the last frozen section's end.<br>• **Larger movement or a shape change** pauses the build. Progress is kept; it never resets.<br>• **Resuming:** the route must reconnect within 2 cm of the last frozen section's end.<br>• **Connection breaks** (more than 4 cm at an anchor): the build pauses, and frozen sections stay as visible scaffold.<br>• **Abandoned scaffold** (no reconnect within 10 s, or the player starts somewhere else): taken down with a short animation. Nothing is lost except that attempt. | No accidental builds while moving. Deliberate holds always complete. A shape change partway through never changes a frozen section. |
| T4 | **Bridge structure and validation.**<br>• A bridge is a **tree of curves**: one curve for a single path, a shared junction plus one curve per branch for a fork.<br>• Each curve passes through the joint positions captured when its section was frozen. Planks, rope, posts and knots are placed along it.<br>• **Checks**, per branch and against the capacity table: both ends anchored, width, slope, clearance, no self-crossing, maximum length.<br>• **Refusal is visible:** Pip shakes his head and the failing segment glows, with shape and motion cues per A7. | The shape matches the route as in I2. Every refusal case is readable. The bake causes no frame hitch. |
| T5 | **Tracking loss and recovery.**<br>1. **Loss:** the active hand is invalid or low-confidence. Affected travelers freeze and grip. The last good hand route stays visible as a **ghost hand** and becomes their temporary support.<br>2. **Guide:** the ghost hand shows where to return your hand.<br>3. **Re-align:** play resumes only when the live route is within 2 cm of the ghost route for 300 ms. Travelers then blend to the live hand over 200 ms.<br>4. **Fallback:** if alignment hasn't happened within 8 s, travelers visibly return to their **last safely reached checkpoint island**. Any partly built bridge is taken down (T3), and the hand gives up control (A3). They never snap to a hand that appeared somewhere else. | Hide your hand, move it 20 cm, show it again: no traveler teleports. Automated test: forcing tracking loss at every point along every route never lets a traveler reach an island it hadn't reached before. |
| T6 **v1.3** | **Hand-size calibration at planting,** from bone lengths, sets the world scale so every gap fits the player's hand. Replanting recalibrates. | Testers with any hand size complete every puzzle. |
| T7 **v1.3** | **Performance.** The competition's minimum is 60 fps. The target is **72 fps or more on Quest 3 and 3S** in every shipped scene and in both modes, including the finale light-run and passthrough. Quest 2 is the development device; its numbers guide the work but can't certify the target devices (Quest 3 renders about 30% more pixels by default). | 72 fps or more in every shipped scene and mode on Quest 3 and 3S (T20). Quest 2 results are reported separately. |
| T8 | **Navigation with hands only,** via A1. When the system menu takes focus, the game pauses. | A full run with no controller ever paired. |
| T9 **v1.3** | **Save and resume:** every bridge's curve tree stored relative to the valley, the ledge state (V2), visitor progress and lit windows (R2, R3), the mode, and the anchor ID (MR3). | Take the headset off mid-puzzle, or quit and relaunch: state and bridges are intact, and the finale and every visitor are still completable. |
| T10 **v1.3** | **Privacy, split by build type.**<br>• **Release build:** the recording code is compiled out, the manifest has no INTERNET permission, nothing is collected, and nothing is stored except save data and the anchor ID. Permissions are only what the shipped modes need: hand tracking, and for Table mode passthrough and anchors. The game shows passthrough but never reads camera images. Scene permission is requested only if the MR2 snap ships.<br>• **Developer build:** local recording (T13) after the tester agrees verbally. The developer exports it over USB, and it's deleted after analysis. | Release-build manifest check: no INTERNET permission, no recording symbols, no permission outside this list. Works fully in airplane mode, including the anchor returning (MR3). |
| T11 **v1.3** | **Stack:** Unity 6000.0.66f2 or later, on Windows, with the Meta XR All-in-One SDK v207, on OpenXR. The Interaction SDK is used for UI and gaze (GZ1–GZ3); passthrough and anchors come from the Core SDK; MRUK only for the MR2 snap. The route, build and traveler systems are custom. | Matches the SDKs suggested in the brief. Every platform feature named in the submission is called at runtime in the shipped build. |
| T12 | **Launches with hands only.** The app manifest declares hand tracking (controllers optional, high tracking frequency). | Plays with controllers switched off. |
| T13 **v1.3** | **Playtest logging (developer builds only):** time to plant, to board, to the first persistent bridge (E20) and time stuck; hint triggers and refused builds; gaze-sign views (GZ1); dropouts as defined in T19; the replay record defined in T17. | Provides the numbers for E1, E2, E8, E12, E20, E21, T14 and T19. |
| T14 | **Anchors placed for tracking.** Reaching for an anchor points the fingers sideways, never straight away from your head. | No anchor requires pointing straight away from your head. Dropout rates show no excess in any finger direction. |
| T15 **v1.3** | **Evidence in the submission,** from the **final build only.** Report N, how many testers were new to hand tracking, and the help given to each (none, verbal, or hands-on). Earlier rounds on other builds are reported separately, or not at all. Testers are counted, never named or shown (the rules bar identifiable people other than entrants). Targets: 80% or more finish Chapter 1, median time 10 minutes or less, disruptive dropouts below the T19 threshold, 0 deaths. | The numbers appear on the video's closing card and in the submission text, with the build version and device. |
| T16 | **X-ray view:** shows the route graph, thresholds, the bridge's curve tree, frozen and uncommitted sections, and build progress. | Judges can turn it on and off. The video shows it for 5–8 s. |
| T17 | **Replay, split into two jobs.**<br>**T17a, test replay:** route, build and traveler logic runs on a **fixed 60 Hz tick in custom kinematic code, with no PhysX in any gameplay-critical path.** Record timestamped joint poses, validity and confidence flags, calibration, level and save state, menu and interaction events, build version and settings; replay feeds the same inputs into the same ticks.<br>**T17b, filming replay:** records traveler transforms, bridge states and animation events every frame and plays them back for the spectator camera. Labeled "replay of recorded play session" in the video. | **T17a:** a recorded failure reproduces the same gameplay decisions on the same build, and the regression test passes after the fix.<br>**T17b:** the filmed replay matches the original session frame by frame. |
| T18 | **Recovering when tracking quality drops.**<br>1. The ghost hand (T5) and Bram's gesture prompt the player to bring the hand back into view.<br>2. If poor quality continues for 20 s or more, one short line of text appears: "Hand tracking works best in a well-lit room, with your hand in view."<br>3. Only the stillness tolerance loosens, at most one step, with a visible icon. Connection distances **never** loosen. | In occlusion and dim-room tests, the player recovers in at most two prompts, and no bridge forms across a visible gap. |
| T19 | **Dropout definition.** A dropout is the active hand invalid or low-confidence for **250 ms or more** while supporting a traveler or building, logged with joints, duration and finger direction. A disruptive dropout froze a traveler or paused a build. Threshold: fewer than 1 disruptive dropout per puzzle. | Both counts are reported for each puzzle. |
| T20 | **Target-device testing** is a production priority. A developer build of the same code shows a small stats panel (fps, dropouts per puzzle, gaze source, mode, build version) and records nothing; the tester reads out or screenshots the numbers. The tester also installs the submission build from the Competition channel invite link. | At least one full Chapter 1 run on Quest 3 and one on Quest 3S, on the submission build, in each shipped mode. If that can't happen, the submission says so, and the risk stays open. |

## Out of scope

| Item | Reason |
|---|---|
| Dam, Shelter, Chapter 2, base building | Cut in v1.3. Visitors give the reason to return with no new verb, and six finished puzzles beat eight rough ones |
| AI/LLM features | Add nothing to the core verb. Best Agentic Interaction isn't targeted |
| Passthrough as the only mode | VR mode ships either way (MR5); Table mode has to pass H5 |
| Forcing a room scan | Space Setup in the first minute would break E21. MRUK is used only when scene data already exists (MR2) |
| Gaze as a required input | Quest 3/3S have no eye tracking. Gaze adds information (GZ1) and an easier menu (GZ2); no puzzle depends on it (I3) |
| Voice input | Needs a microphone permission and speech services, against T10 |
| Multiplayer | Network risk with no gain to the core |
| Hand-to-hand contact | Where tracking is weakest |
| Timers, leaderboards, fail states, streaks | Conflict with E7, accessibility and the calm tone |
| Procedural levels | Hand-authored puzzles and visitors score better |
| Controller polish | No judging credit |

## Decisions

- **Concept:** Palmfolk. Six puzzles: Board, First Bridge, Width, Fork, Arch, Finale. Puzzles are referred to by name, because "P" numbers belong to Polish.
- **v1.3 additions are the last.** Planting, visitors, eyes and Table mode are in. From here only corrections, removals, and EX3 and EX4 through their gates (build plan).
- **Requirements lock at M1.** Headset results set the final numbers: Quest 2 at M1, then Quest 3/3S at M1b, which takes priority.
- **Modes:** VR mode is the floor. Table mode becomes the default only if H5 passes on a Quest 3 or 3S; with Quest 2 results only, it ships as an option labelled as such, or is cut.
- **Claims follow tests.** Nothing is described as working on a device it didn't run on. Meta VR Glasses are a design target (FoV, eyes and hands), never a tested device.
- **I7 design check kept.** Character names and hand material: owner's choice.
- **Licensing:** original Palmfolk code is MIT. Dependencies and assets keep their own licences and notices (Unity terms, Meta SDK licence, third-party assets), listed in the credits (P9). Check that a licence allows redistribution in an APK before an asset goes in.
- **Sign-off rule:** any change after M5 reopens M5 for everything it affects (build plan).
- ⚑ **Pending:** privacy-policy URL (check when the Competition channel is created; the release build collects nothing, T10).
